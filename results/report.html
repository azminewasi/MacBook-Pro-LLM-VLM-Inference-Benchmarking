Key findings

  • Quality scales with size, with one twist. GSM8K without thinking rises 54% → 77% → 85% → 88%. The 9B at 4-bit is the best text model and is faster (26 tok/s) and smaller in memory (5.5 GB) than the 4B in bf16 (14 tok/s, 8.5 GB): on a 16 GB laptop, quantising up is better than running a smaller model at full precision.
  • Thinking helps vision for the smaller models but looks harmful on text under a fixed token cap. AI2D thinking off→on (the 9B already answers directly at 82%): 0.8B 41%→48%, 2B 46%→73%, 4B 45%→85%. On GSM8K thinking lowers accuracy at the 3,072-token cap (0.8B 54%→22%, 9B 88%→70%) because up to 94% of the thinking runs never finish.
  • The cap, not the capability, is the problem. With an 8x larger budget (first 20 questions) thinking becomes the best mode and the 9B catches up with the 4B (both 95% on GSM8K): GSM8K 4B 70%→95%, 9B 65%→95%, with no 9B sample truncated. The price is time: ~131 s per answer at 1x grows to ~410 s at 8x for the 4B.
  • Remaining truncations are mostly repetition loops. At 8x, 34 of 39 truncated 0.8B–4B outputs end in a repeating loop (compression-ratio test), while at 1x most truncations are legitimate long reasoning. The 9B almost never loops.
  • Wrong answers are long answers. In thinking mode wrong answers use about 1.9x the tokens of correct ones, which is why more budget alone has diminishing returns.
  • Speed is a memory-bandwidth story. Decode tok/s × weight bytes lands at 112–143 GB/s for every model, i.e. most of the chip's peak bandwidth; speed halves when weights double.
  • The 16 GB limit is felt from the 4B up. The 4B in bf16 peaks at 9.4 GB of MLX memory and macOS used up to ~2.4 GB of swap (the 9B runs showed ~2.3 GB too, with only 6.5 GB of MLX memory, so that is system-wide pressure). Decode speed stayed flat (~14 tok/s for the 4B), so the swap held idle pages, not the model. 0.8B and 2B never touched swap.

1. Setup

Apple M5 (10-core CPU/GPU), 16 GB unified memory, macOS (Darwin 25.6), on AC power, other apps closed. MLX 0.32 / mlx-vlm 0.7.12, all models served from the same multimodal checkpoint. GSM8K: first 100 test questions, exact match on the final number. AI2D: first 100 test items, options numbered 1–4 (25% chance level). Thinking off is greedy; thinking on samples at T=0.6, top-p 0.95. Caps: off 512 / 32 tokens, on 3,072 / 2,048 (GSM8K / AI2D); the long-thinking runs use 8x those caps on the first 20 questions. A truncated answer counts as wrong.

Read AI2D thinking-off with care. It is a 32-token budget: the 4B starts explaining before answering and gets cut off in 49% of cases, so its 45% reflects the format limit, not weak vision. The 9B answers directly (82%); the 0.8B and 2B are near chance. All cells have n=100, so 95% intervals are about ±10 points.

What are the truncated outputs doing?

A truncated thinking trace is classed as a repetition loop if its last 3,000 characters compress to under 15% of their size (zlib), i.e. the model is repeating itself; otherwise it is long but not looping.

GPU utilisation was 97–99% for every thinking-on run and CPU utilisation 6–12% (the CPU only feeds the GPU), so generation is fully GPU-bound. The thermal speed limit never dropped below 100%, so the M5 did not throttle even on multi-hour runs. The 9B at 4-bit uses only 5.5 GB of weights, which leaves room for long contexts.

Throughput is a hard physical ceiling: decoding streams all weights for every token, so at thinking-on speeds the machine generates about 6.1 M tokens/day with the 0.8B, 2.6 M with the 2B, 1.2 M with the 4B and 2.2 M with the 9B (4-bit).

Cost scales with generated tokens, not prompt size. Short-answer multiple-choice with thinking off (AI2D off: a few tokens) is cheap for every model; chain-of-thought math (GSM8K on: ~2,000 tokens) is 100-1000x more expensive per question. When choosing an evaluation set for this machine, estimate answer length first.

Verdict

  • Comfortable: bf16 models up to 2B (4-7 GB free) and a 4-bit 9B (3 GB free); thinking traces up to 25k tokens; multi-hour unattended runs on AC power with no throttling.
  • Tight: 4B in bf16 (about 9.4 GB with a long generation; macOS started swapping but decode speed did not drop), and, by extrapolation, 14B-class at 4-bit or 8B-class at 8-bit (~8.5 GB of weights): anything above ~8 GB of weights.
  • Not possible: 9B in bf16 (about 19 GB) and 32B-class models even at 4-bit.
  • Slow, not impossible: thinking-mode evaluation of the larger models: a full GSM8K test split with the 4B thinking on takes about 48 h at 1x caps and much longer at 8x. Sample 100 questions, as done here, or run non-thinking.
  • Not measured here: batched or concurrent generation (decode is bandwidth-bound, so batching should raise total throughput substantially but was not tested), contexts beyond ~25k tokens, images larger than 896 px (images were downsized), power draw in watts, battery operation, and sustained load longer than the ~6 h single runs.

TermMeaning

Prefill tok/sPrompt tokens processed per second before generation starts (compute-bound).
Decode tok/sGenerated tokens per second after the first token (memory-bandwidth-bound).
Latency / p95End-to-end time per request (mean, and 95th percentile).
Capped / truncatedThe model hit the max-token limit before finishing; counted as wrong unless a correct final answer already appeared.
Acc. if finishedAccuracy over only the samples that finished within the cap (not truncated).
Peak GBPeak MLX (GPU) memory allocation during a request, from mx.get_peak_memory().
RAM / SwapSystem RAM used and swap used (psutil), sampled every 0.5 s; maximum over the run.

Therm. limitmacOS CPU speed limit from pmset; 100% = no thermal throttling.
